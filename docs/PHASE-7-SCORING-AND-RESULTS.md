# Phase 7: finalized scoring and results

**No finalized attempt = no score.** The permanent owner rule from [Phase 6](PHASE-6-INTERACTIONS-AND-FINALIZATION.md#permanent-owner-rule) still applies. An answer, Review navigation, or a section lock does not load a scoring bank, calculate a score or show any correctness. Early End Exam and exact-deadline timeout go through the same durable finalization path; only a persisted, immutable, validated terminal snapshot can be handed to the scorer. A valid persisted result is read back on reload rather than re-scored. The scoring version travels with it.

## Policy

- Unit weight: one point per question. Single choice uses immutable option identity. Multiple-choice uses exact set; dropdown, dropdown HOTSPOT, matching, drag/drop, and statement use exact full mappings; ordering uses exact ordered item IDs. A diagram-dependent interaction retains its reviewed nested answer type. No partial credit. Unanswered is zero credit; malformed, incomplete and extra selections do not receive credit. Missing or invalid authoritative definitions fail closed rather than silently reducing the denominator.
- The actual finalized question count is the denominator. Empty attempts cannot score. Section and interaction summaries include only categories present in that attempt. Pass is calculated centrally from the unrounded percentage compared with the explicitly configured threshold. Display is rounded centrally to at most two decimal places; display rounding never changes pass/fail.
- The public demo uses an explicitly fictional 75% threshold and a synthetic, lazily loaded answer fixture. It contains no real source keys. A real examination threshold is not assumed or represented as a Microsoft standard.
- `postExamReviewPolicy` is explicit and defaults to `NONE`. Candidate results in this milestone are aggregate only. More permissive names are reserved for a separately authorized and implemented review feature; setting a name never publishes correct answers or explanations.

## Local protected verification

The authorized development reference continues to contain exactly 59 items. There is no promotion of held material and no image-coordinate HOTSPOT. Source option/target/item IDs, not labels or shuffled indexes, drive comparison. The protected builder independently checks the pinned Phase 3 bank, display and reference. If an explicit local `EXAM_PASSING_PERCENTAGE` is set, it also validates the separately digest-pinned scoring projection, matches selected rows to the aggregate source mappings, verifies those IDs against reviewed display contracts, and creates a **separate** `candidate-scoring.js` for the verified development reference. No explanations or raw source records are projected. Do not upload that file.

Use the [local Phase 5 runbook](PHASE-5-CANDIDATE-EXAM.md) for guarded build and serving. An approved deliberate local scoring run can set `EXAM_PASSING_PERCENTAGE` to a number from 0 through 100, with up to four fractional digits, and leave `EXAM_DURATION_MINUTES` optional per Phase 6. No threshold means protected scoring is disabled. Once a result is saved, changing later configuration does not alter that result. Use different local origins if separate test attempts must remain independent; do not clear existing candidate data to run a test.

The optional protected scoring module is loaded by the normal application only after durable finalization, on the approved device’s loopback server. This is not a secrecy claim: someone with access to that local directory or origin can directly inspect its static files, browser state or clock. No real keys, PDFs, protected banks, or scoring modules belong in Git, CI, GitHub Pages, or public screenshots. There is no backend or exam-integrity guarantee. No deployment or merge was part of this milestone.
